## 我对 scoreboard 的理解

用自己的话回答：

- scoreboard 的职责是什么？
- expected 和 actual 分别从哪里来？
- 为什么"人肉看波形"不算合格验证，scoreboard 自动比对才算？
- 为什么必须故意制造一个 FAIL 场景？

我的理解：

```text
score的职责是通过发送随机激励，收集正确的示例和实际的输出，进行对比，观察dut是否正确
expect来自reference_module,actual来自monitor拿取的dut输出
波形难看，激励太多，一个一个看不现实
防止一切行为scoreboard都算正确，scoreboard也要有能抓住错误的能力

补充修正：

```text
- 第1行"发送随机激励"是 driver 的职责，不是 scoreboard 的：scoreboard 不驱动任何东西，它是裁判，只负责拿期望值和实际值比对、计数 PASS/ERROR。
- 其余三行都对：expect 来自 reference_model，actual 来自 monitor 采的 DUT 输出；人肉看波形不现实；FAIL 场景防止"什么都算对"。
```
```

## 我对 reference model 的理解

用自己的话回答：

- reference model 是什么？它和 DUT 的关系是什么？
- 期望值是怎么算出来的？
- 本次透传 DUT 的 reference model 为什么这么简单？

我的理解：

```text
reference是通过c语言或者sv写出的绝对正确的对照组，用来对比看待dut是否实现正确
期望值通过理解dut的逻辑，reference实现的
因为dut就很简单

补充修正：

```text
- 期望值应来自"规格/功能描述"，不是 DUT 的 RTL 实现——照 RTL 写 reference 会把 DUT 的 bug 一起抄进去，FAIL 场景就测不出来了。
- reference 不是天生"绝对正确"，它是你基于规格写的对照模型；写错 reference，比对结果照样错，所以 reference 本身也要 review。
- "因为dut就很简单"对：透传 DUT 的期望输出就是输入原值，所以 reference 只有几行。
```
```

## 我对两路 mailbox 配对的理解

用自己的话回答：

- scoreboard 为什么可以按顺序 get 两路（expect_out 和 actual_out）就自动配对，不用额外对齐？
- 输入 monitor 在 t=35 采、输出 《 在 t=45 采，错开一拍，为什么比对还是对的？

我的理解：

```text
因为我用了两个mailbox,这两个是分开运行的
因为对比的时候，输入monitor的值在一个周期内的时间是一样的。。。。哎是为什么,哦哦我知道了，因为get是阻塞取值，，而且也不是输入输出Monitor比啊，是理论值和实际值比啊

补充修正：

```text
- 第1行没答到点：能按顺序配对，前提是输入和输出"1:1 且有序"——每笔输入恰好产生一笔输出、顺序不变、不会乱序/合并/拆开；两个 mailbox 只是两个队列，让它们对上的是数据的这种有序性。
- 第2行其实答对了：错开一拍没关系，因为(1) 比的是"期望值 vs 实际值"，不是"输入 vs 输出"；(2) get() 阻塞，期望值先到了就等着，直到实际值那笔到了才配对。延迟被 get() 的等待吸收。
``` ```

## 今日结论

用 3 到 5 句话总结今天学到了什么。

```text
scoreboard 是验证环境的裁判：从 expect_out 拿期望值、从 actual_out 拿真实输出，逐笔比对并计数 PASS/ERROR，是"自动判断对错"的核心。
reference model 根据输入 transaction 算期望输出；对透传 DUT，期望值就是输入数据本身，所以 reference 简单到只有几行。
只有 PASS 场景不能证明 scoreboard 有用，故意把 DUT 改成 data+1 后 48 笔全部报 Mismatch、ERROR 48，证明它能抓住错误。
mailbox 的 get() 是 task 不是 function，不能当表达式用，必须用输出参数形式 mb.get(x)。
两路 get 按顺序配对就能对齐，因为输入和输出是 1:1 有序的；输入 t=35 采、输出 t=45 采，错开一拍但笔数一致。
```
