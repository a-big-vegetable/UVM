## 我对 transaction 的理解

用自己的话回答：

- transaction 是什么？
- 为什么验证环境里不直接到处传 `data` 裸信号，而要封装成 transaction？
- 本次 `transaction` 类里有哪些字段？
- `randomize()` 对 transaction 做了什么？

我的理解：

```text
transaction是一种类，可以把复杂的传输数据打包起来，方便数据的流通
到处传data，如果只有一个data还好，但如果有十来个数据，到处传输就会显得杂乱且容易错误，遗漏，被错改。所以封装成transaction始终就只有一个类，到driver的时候再拆分就行。
只有data字段
随机化了transaction里的data
```

## 我对 driver 的理解

用自己的话回答：

- driver 的职责是什么？
- driver 和 DUT 的区别是什么？
- driver 和 monitor 的区别是什么？
- 本次 driver 如何把 `transaction.data` 变成 `vif.valid/vif.data` 上的时序？

我的理解：

```text
driver负责把transaction已经打包的数据解包出来，然后随机化数据产生激励，并传给dut
driver是类，是仿真相关的，不会被综合，class就是RTL，会被综合。driver就发送激励，dut就接受激励
driver发送激励，monitor什么都不参与，就纯纯负责抓取输入输出的数据用来比对
在function里面，给vif进行非阻塞赋值

补充修正：

```text
- "class就是RTL，会被综合"写反了：class 是验证代码，不可综合；module/DUT 才是 RTL、可综合。
- "在function里面给vif赋值"不准：实际是在 task run() 里赋值。驱动带 @(posedge) 时序控制，function 不允许时序控制，只有 task 可以。
- 更准确的分工：driver 把 transaction 翻译成 vif.valid/vif.data 上的时序；随机化来自 pack.randomize()，理想架构里随机化由 generator/sequence 负责。
```
```

## 我对 virtual interface 的理解

用自己的话回答：

- 为什么 class 里的 driver 不能像 module 一样直接连端口？
- `virtual valid_ready_if.drv_mp vif;` 这句话是什么意思？
- 为什么构造函数里要写 `this.vif = vif;`？
- `drv_mp` 在这里限制了哪些方向？

我的理解：

```text
因为driver是class类，直接连接接口是不符合仿真原理的，直接的vif是要被综合出来逻辑电路的
定义一个虚接口，采用drv_mp的方向
把虚接口和外部数据接口连在一起，才能发送过去激励

补充修正：

```text
- "要被综合出来逻辑电路"不对，与综合无关：class 是动态对象，没有 module 那样的端口列表，无法用连线挂进层次结构。virtual interface 只是一个句柄，通过构造函数 new(vif) 把它绑定到 tb_top 里真实的 interface 实例，class 才能访问 vif.valid/vif.data。
- 第3行更准确：new(vif) 把虚接口句柄和真实 interface 实例绑在一起后，driver 才能驱动激励。
```
```

## 本次握手时序

结合 `vcs_run.log` 回答：

- 第 1 笔 transaction 的随机 data 是多少？
- 第 1 笔数据在哪个时间点被 driver 放到 `vif.data`？
- 哪个时间点 `valid && ready` 成立？
- DUT 的 `data_out` 什么时候变成这笔 data？

我的分析：

```text
第一笔数据是在调用完成rst_n的时候，再经过一个时钟周期，开始随机化赋值
在数据给vif.data成功后valid变为1，此时因为rst_n = 1，ready也为1，握手成功
在握手成功的后一个周期

补充修正：

```text
- 第 1 笔 transaction 的随机 data 是 0x7a60f241（log：transaction.data = 0x7a60f241）。
- 精确时间点：t=20 rst_n 拉高并调用 run() 随机化；t=25 posedge driver 把 data 放到 vif.data（非阻塞赋值在本时刻末生效）；t=35 posedge DUT 采样到 valid&&ready，data_out 更新（log 在 t=36 显示）。
- "握手成功"严格说是 t=25 末到 t=35 窗口内 valid&&ready 均为 1，DUT 在 t=35 边沿真正捕获。
```

## 今日踩坑

至少写 3 条。

1. function，new等过程要放在Initial里面
   - 补充修正：更准确的说法是——含时序控制（@、#）的驱动代码必须放在 task 里（function 不允许时序控制），task/function 再由 initial/always 调用；new() 的调用语句同样要放在过程块里。
2. 在new里传入interface的时候，也要把方向说清楚

补充修正：

- 它只是声明一个句柄（指针），指向真实 interface 实例，不会产生硬件。drv_mp 表示驱动视角：valid/data 输出，ready/rst_n/clk 输入。
```
```

```systemverilog
if (!pack.randomize()) begin
    $fatal("pack.randomize fatal");
end
```

我的解释：

```text
如果随机化失败(randomize返回值为1)，就直接结束仿真

补充修正：

```text
- 写反了：randomize() 返回 1 表示成功，返回 0 表示失败。!pack.randomize() 只有在 randomize() 返回 0（失败）时才为真，才会触发 $fatal。即"随机化失败就结束仿真"。
```
```

```systemverilog
@(posedge vif.clk iff vif.ready == 1);
```

我的解释：

```text
当ready==1时候，说明两边已经握手成功，此时数据已经无效了，把valid=0

补充修正：

```text
- 握手成立要 valid && ready 同时为 1。此时 valid 已在上一拍被 driver 置 1，所以这条语句是"等到某个 posedge 上 ready 也为 1"，即握手成立，随后把 valid 拉低结束这笔传输。
```
```
