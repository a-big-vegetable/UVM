## 我对 interface 的理解

用自己的话回答：

- interface 是什么？
- 它解决了不用 interface 时的什么问题？
- 为什么说 interface 只是信号封装，不应该乱写 driver/DUT 行为？

我的理解：

```text
interface是为了解决书写RTL代码时，接口过多，容易错误且不直观，抽象了一个通用的接口出来。为了解决不同模块同一信号但方向不同的问题，还可以使用moport语法。且，使用的moport要放在模块端口声明的地方，top就使用正常的实例化就行了
实际信号的变化应当由模块自己确定，interface只负责信号封装是职责明确的表现，这样做可以避免两个模块对同一个信号赋值。
```

补充修正：

```text
interface 不只是为了 RTL，也服务于 testbench。它把 DUT、driver、monitor 都要用的一组信号封装起来，减少端口连接错误。
modport 拼写是 modport，不是 moport。
interface 可以包含信号、modport、clocking block、assertion/coverage，但不应该随便写某个角色的驱动行为。
```

## 我对 modport 的理解

用自己的话回答：

- modport 是什么？
- `valid_ready_if.dut_mp vif` 这句里，方向限制在哪里生效？
- 为什么 tb_top 例化 DUT 时写 `.vif(vif)`，而不是 `.vif(vif.dut_mp)`？

我的理解：

```text
modport是声明端口方向的一种语法，可以理解为只是一种视角，不是真正有这么个东西，所以传输的连接的时候还是要写vif这个实例
```

补充修正：

```text
方向限制在模块端口声明处生效，例如：
module dut(valid_ready_if.dut_mp vif, ...);

tb_top 里连接时传完整 interface 实例：
.vif(vif)

因为 vif 是真实 interface 实例，dut_mp 是 DUT 看这个 interface 的视角，不是另一个独立实例。
```

## 我对 valid-ready 握手的理解

用自己的话回答：

- `valid` 表示什么？
- `ready` 表示什么？
- 为什么只有 `valid && ready` 同时为 1 时，才算一笔数据传输成功？
- 本次仿真里，哪一拍发生了握手？

我的理解：

```text
valild表示driver那里的信号准备好了，ready表示dut现在处于可以接收信号的过程。这是一个握手，只有两边都有效才能进行信号的传输

```

补充修正：

```text
valid 表示发送方当前放在 data 上的数据有效，不只是“准备好了”。
ready 表示接收方当前可以接收数据。
当 valid && ready 在同一个时钟采样点为 1 时，这一拍完成一笔传输。
本次仿真中，25ns 附近输入侧 valid=1、ready=1、data=0x12345678，因此发生了一次输入握手。
```

## 我对 DUT 的理解

用自己的话回答：

- 这个 `dut` 的功能是什么？
- `ready` 为什么由 DUT 驱动？
- `valid_out/data_out` 为什么用 `always_ff` 和非阻塞赋值？
- 为什么不能把全部逻辑都写成 `always_comb`？

我的理解：

```text
dut的功能是把信号卡一拍再传出去
ready就代表着dut空闲，可以处理信号
因为要存着数据
```

补充修正：

```text
这个 DUT 是最小透传/打一拍模块：当输入侧 valid && ready 成立时，DUT 在时钟边沿采样 data，并在输出侧给出 valid_out 和 data_out。
ready 由 DUT 驱动，因为 DUT 是接收方，只有 DUT 知道自己能不能收。
valid_out/data_out 用 always_ff，是因为它们要保存某个时钟边沿采到的结果；用非阻塞赋值 <= 是为了模拟寄存器在同一时钟边沿同时更新。
如果全部写成 always_comb，要么 data_out 无法保存上一拍数据，要么容易推导 latch 或产生多驱动。
```

## 关于 `$display` 和 `#1`

用自己的话回答：

- 为什么 `$display` 和 `always_ff` 同在 `posedge clk` 触发时，可能看到旧值？
- `#1` 放在 `$display` 前面解决了什么问题？

我的理解：

```text
因为$display的触发也是在时钟上升沿，和非阻塞赋值一样。所以在同在时钟上升沿结束触发的话，寄存器值还没更新，display出来的是旧的值，故要多等一ns
```

补充修正：

```text
更准确地说：always_ff 中的非阻塞赋值会在 NBA 区域更新，而同一时刻的 $display 可能先读到旧值。
#1 的作用是把打印延后 1ns，避开同一时刻的调度竞争，观察到寄存器更新后的值。
```
